# Схема базы данных Fridgy

## Назначение

Схема предназначена для приложения домашней инвентаризации продуктов. Она должна поддерживать:

- общий каталог продуктов и поиск по штрихкоду;
- пищевую ценность на 100 г или 100 мл;
- несколько домохозяйств и несколько участников;
- общие и персональные продукты внутри домохозяйства;
- отдельные экземпляры одинакового продукта с разными сроками годности;
- учёт текущего остатка и неизменяемую историю его изменения;
- расчёт пищевой ценности фактически употреблённого количества.

## Связи

```text
User ──< HouseholdMember >── Household ──< PantryItem >── Product
                                          │
                                          └──< InventoryEvent

Product ── ProductNutrition
```

Всего в начальной схеме семь таблиц.

> Для первичных ключей рекомендуется UUID, особенно с учётом мобильного API. Если проект останется централизованным и офлайн-синхронизация не потребуется, UUID можно заменить на Django `BigAutoField` до создания первых миграций.

## 1. `users`

Пользователи приложения. Таблица реализуется кастомной моделью Django `accounts.User`, унаследованной от `AbstractUser`. Вход выполняется по e-mail, поле `username` не используется.

| Колонка | Тип PostgreSQL | Обязательность | Назначение |
|---|---|---:|---|
| `id` | `UUID` | да | Первичный ключ |
| `email` | `VARCHAR(254)` | да | Уникальный адрес и идентификатор для входа |
| `display_name` | `VARCHAR(120)` | нет | Отображаемое имя |
| `created_at` | `TIMESTAMPTZ` | да | Дата регистрации |

Хеш пароля, признаки активности, персонал и суперпользовательские права, группы и разрешения предоставляет `AbstractUser`. Подтверждение e-mail и социальные аккаунты не дублируются в этой таблице: их хранит `django-allauth`.

Ограничения:

- `PRIMARY KEY (id)`;
- уникальность нормализованного e-mail без учёта регистра.

## 2. `households`

Домохозяйство объединяет пользователей и принадлежащие им запасы.

| Колонка | Тип PostgreSQL | Обязательность | Назначение |
|---|---|---:|---|
| `id` | `UUID` | да | Первичный ключ |
| `name` | `VARCHAR(120)` | да | Название домохозяйства |
| `created_at` | `TIMESTAMPTZ` | да | Дата создания |

Отдельная колонка `created_by_id` не требуется: владелец домохозяйства определяется ролью в `household_members`.

## 3. `household_members`

Связь пользователей с домохозяйствами и их роль внутри каждого домохозяйства.

| Колонка | Тип PostgreSQL | Обязательность | Назначение |
|---|---|---:|---|
| `id` | `UUID` | да | Первичный ключ |
| `household_id` | `UUID`, FK | да | Ссылка на `households.id` |
| `user_id` | `UUID`, FK | да | Ссылка на `users.id` |
| `role` | `VARCHAR(16)` | да | `owner` или `member` |
| `joined_at` | `TIMESTAMPTZ` | да | Дата вступления |

Ограничения:

- `UNIQUE (household_id, user_id)`;
- значение `role` входит в `owner`, `member`;
- домохозяйство должно иметь хотя бы одного участника с ролью `owner` — это контролируется сервисным слоем.

## 4. `products`

Глобальный справочник продуктов. Один продукт может использоваться во многих домохозяйствах и экземплярах запасов.

| Колонка | Тип PostgreSQL | Обязательность | Назначение |
|---|---|---:|---|
| `id` | `UUID` | да | Первичный ключ |
| `barcode` | `VARCHAR(32)` | нет | Уникальный штрихкод; `NULL` для продукта без штрихкода |
| `name` | `TEXT` | да | Основное название |
| `brand` | `TEXT` | нет | Бренд |
| `package_quantity` | `NUMERIC` | нет | Количество в стандартной упаковке |
| `package_unit` | `VARCHAR(16)` | нет | `g`, `ml` или `pcs` |
| `image_url` | `TEXT` | нет | Ссылка на изображение продукта |
| `source_updated_at` | `TIMESTAMPTZ` | нет | Время последнего изменения во внешнем источнике |
| `created_at` | `TIMESTAMPTZ` | да | Время создания записи |
| `updated_at` | `TIMESTAMPTZ` | да | Время последнего локального обновления |

Штрихкод хранится строкой, а не числом, чтобы сохранять ведущие нули и поддерживать разные форматы кодов.

Ограничения:

- уникальность `barcode`, когда значение задано; PostgreSQL допускает несколько записей с `barcode IS NULL`.

Корректность количества и согласованность количества с единицей проверяются на уровне API, интерфейса и импорта, а не ограничениями базы данных.

В основную модель не переносятся служебные поля Open Food Facts, редакторы, статистика сканирований, debug/OCR-поля, экологические расчёты и сотни тегов.

## 5. `product_nutrition`

Пищевая ценность продукта. Связь с продуктом — один к нулю или одному: запись отсутствует, если данных о пищевой ценности нет.

| Колонка | Тип PostgreSQL | Обязательность | Назначение |
|---|---|---:|---|
| `id` | `UUID` | да | Первичный ключ |
| `product_id` | `UUID`, FK | да | Уникальная ссылка на `products.id` |
| `basis_unit` | `VARCHAR(8)` | да | Основа значений: `100g` или `100ml` |
| `energy_kcal` | `NUMERIC` | нет | Энергетическая ценность |
| `protein_g` | `NUMERIC` | нет | Белки |
| `fat_g` | `NUMERIC` | нет | Жиры |
| `saturated_fat_g` | `NUMERIC` | нет | Насыщенные жиры |
| `carbohydrates_g` | `NUMERIC` | нет | Углеводы |
| `sugars_g` | `NUMERIC` | нет | Сахара |
| `fiber_g` | `NUMERIC` | нет | Клетчатка |
| `salt_g` | `NUMERIC` | нет | Соль |
| `updated_at` | `TIMESTAMPTZ` | да | Время последнего обновления |

Связь `OneToOne` обеспечивает уникальность `product_id`. Проверка диапазонов нутриентов выполняется на уровне API, интерфейса и импорта. Допускается создать запись без заполненных нутриентов, если значения ещё не известны.

`energy_kj` не хранится отдельно, так как вычисляется из килокалорий. `sodium` на первом этапе также не хранится отдельно: для пользовательского интерфейса используется соль.

Расчёт употреблённой пищевой ценности:

```text
значение нутриента = съеденное количество / 100 × значение нутриента на 100 г или 100 мл
```

Расчёт возможен только тогда, когда единица количества экземпляра соответствует `basis_unit` пищевой ценности.

## 6. `pantry_items`

Конкретный экземпляр продукта в доме. Несколько записей могут ссылаться на один `Product`, но иметь разные сроки годности, остатки и владельцев.

| Колонка | Тип PostgreSQL | Обязательность | Назначение |
|---|---|---:|---|
| `id` | `UUID` | да | Первичный ключ экземпляра |
| `household_id` | `UUID`, FK | да | Домохозяйство, где хранится продукт |
| `product_id` | `UUID`, FK | да | Ссылка на справочный продукт |
| `holder_id` | `UUID`, FK | нет | Владелец экземпляра; `NULL` означает общий продукт |
| `remaining_quantity` | `NUMERIC` | да | Текущий остаток |
| `quantity_unit` | `VARCHAR(16)` | да | `g`, `ml` или `pcs` |
| `expiry_date` | `DATE` | нет | Дата окончания срока годности |
| `expiry_type` | `VARCHAR(16)` | нет | `best_before` или `use_by` |
| `storage_location` | `VARCHAR(32)` | нет | `fridge`, `freezer`, `pantry` или `other` |
| `status` | `VARCHAR(16)` | да | `active`, `consumed` или `discarded` |
| `opened_at` | `TIMESTAMPTZ` | нет | Когда упаковка была открыта |
| `note` | `TEXT` | нет | Пользовательский комментарий |
| `created_at` | `TIMESTAMPTZ` | да | Время добавления |
| `updated_at` | `TIMESTAMPTZ` | да | Время последнего изменения |

Правила:

- `remaining_quantity >= 0`;
- `holder_id`, если задан, должен принадлежать тому же домохозяйству через `household_members`;
- `status = active` означает, что экземпляр присутствует в запасах;
- при полном употреблении статус становится `consumed`, при полном списании — `discarded`;
- общий продукт определяется как `holder_id IS NULL`.

Проверка принадлежности держателя домохозяйству выполняется сервисным слоем, поскольку обычный внешний ключ не может выразить это межтабличное условие.

Индексы:

```text
(household_id, status, expiry_date)
(household_id, holder_id, status)
(product_id, status)
```

Первый индекс используется для общей сводки и сортировки по сроку годности, второй — для фильтра «мои продукты», третий — для поиска активных экземпляров после сканирования штрихкода.

## 7. `inventory_events`

Неизменяемая история действий с конкретным экземпляром продукта.

| Колонка | Тип PostgreSQL | Обязательность | Назначение |
|---|---|---:|---|
| `id` | `UUID` | да | Первичный ключ |
| `pantry_item_id` | `UUID`, FK | да | Ссылка на `pantry_items.id` |
| `performed_by_user_id` | `UUID`, FK | да | Пользователь, совершивший действие |
| `event_type` | `VARCHAR(16)` | да | `added`, `consumed`, `discarded` или `adjustment` |
| `quantity_delta` | `NUMERIC` | нет | Изменение остатка со знаком |
| `occurred_at` | `TIMESTAMPTZ` | да | Время действия |
| `note` | `TEXT` | нет | Комментарий |

Примеры:

```text
added      +1000 ml
consumed    -250 ml
discarded   -100 ml
adjustment   +50 ml
```

Единица события отдельно не хранится: она всегда совпадает с `pantry_items.quantity_unit`. Это исключает противоречивые данные.

Правила:

- события не редактируются и не удаляются обычными пользовательскими операциями;
- `performed_by_user_id` должен быть участником домохозяйства экземпляра;
- `remaining_quantity` и событие создаются или обновляются в одной транзакции;
- после операции остаток не может стать отрицательным;
- событие `added` фиксирует исходное количество, поэтому отдельная колонка `initial_quantity` в `pantry_items` не нужна.

Индекс:

```text
(pantry_item_id, occurred_at)
```

## Границы первой версии

На первом этапе не создаются отдельные таблицы для:

- переводов названий;
- ингредиентов и аллергенов;
- категорий и тегов;
- уведомлений;
- аналитических агрегатов;
- внешних импортов и исходных JSON-записей.

Эти сущности следует добавлять только вместе с пользовательской функцией, которой они действительно нужны. Импорт `baltics_products.jsonld` на первом этапе заполняет только полезные поля `products` и `product_nutrition`; отсутствие большинства полей является допустимым состоянием.
